# 写真を単体で送るのをやめたときの検証

送信ペイロードから `photo_base64` を外した改修の検証記録。写真は入稿 PDF
（`print_base64`）の中に 350 dpi で入っており、GAS 側もすでに保存をやめていた
——同じ絵を1回の注文で2度送っていたのをやめた、というだけの改修。

変えたのは**送るもの1つ**だけ。入稿データの中身・画面の見た目・操作には手を
入れていない。それを実測で確かめたのがこの記録。

## 検証のやり方

改修前と改修後の**それぞれを本番ビルドして headless Chromium で実際に操作し**、
「送信する」を押して飛んだ POST を受け取って中身を実測している。見た目や
ペイロードを別スクリプトで真似て比べる方法は使っていない。

```
next build → next start (:4598)
  ↓ Playwright で Step1〜Step5 を実操作（写真アップロード含む）→「送信する」
GAS の代わりに立てたローカルサーバ (:4599) が POST body をそのまま保存
  ↓
payload を JSON として実測 / print_base64 を PyMuPDF で画像化して画素比較
```

- 写真は `public/sample-meishi.png` の写真枠を切り出したもの（962 × 823px）。
  1匹・2匹・3匹すべてで**同じ絵を各区画に入れる**ので、カードは毎回同じになる。
- 文言も実物名刺にそろえてある（トイプードル／ペコ、ポメラニアン／コテツ、
  柴犬／こたつ、鈴木太郎、ペコ★トイプードル、@peco_channel）。
- 各条件 **3回**ずつ走らせて中央値を採り、生の3値も併記している。

### 回線

送信時間は回線で決まる部分が大きいので、2つの条件で測った。

| | 上り | 下り | 遅延 |
|---|---|---|---|
| localhost | 制限なし | 制限なし | 0 |
| 携帯回線 | 750 kbit/s | 1.6 Mbit/s | 150 ms |

携帯回線は CDP の `Network.emulateNetworkConditions` で作っている。タレントが
実際に使うのはこちら側の条件。

なお携帯回線の測定では、**同じ注文を1回フルスピードで通してから2回目を測って
いる**。入稿 PDF を描くときテンプレート・リボン・フォント・ロゴを取りに行くので、
それを絞った回線で毎回取りに行かせると、測りたいもの（POST そのもの）が埋もれる
ため。

### 何を時間として測っているか

「送信する」を押してから POST を送り終わるまでを、中で起きている2つに分けている。

- **build** … 入稿 PDF を描いて、payload を JSON 文字列にするまで
- **send** … POST そのもの（`PerformanceResourceTiming` の実測）

`build + send` が「送信にかかる時間」。完了画面が出るまでの時間はこれより
0.4〜0.7秒長いが、その差は**送信後に完成カードの絵を描いている分**で、この改修
とは関係しない（`app/page.tsx` で POST 後に別途描いている）。

## 1. 送信されるデータ（実際に飛んだ POST）

```
改修前 keys: ['adjust', 'ig_handle', 'ig_name', 'line_user_id', 'owner_name',
              'pets', 'photo_base64', 'print_base64']
改修後 keys: ['adjust', 'ig_handle', 'ig_name', 'line_user_id', 'owner_name',
              'pets', 'print_base64']
```

`photo_base64` だけが無くなり、他は増えても減ってもいない。

| キー | 1匹 | 2匹 | 3匹 |
|---|---|---|---|
| `ig_handle` / `ig_name` / `owner_name` / `pets` / `adjust` / `line_user_id` | 完全一致 | 完全一致 | 完全一致 |
| `photo_base64` | 1,861,352 → **削除** | 1,302,604 → **削除** | 1,015,848 → **削除** |
| `print_base64` | バイト列は不一致（→ 3章で画素比較） | 同左 | 同左 |

**受入基準1（送信されるデータに写真が含まれていない）** ✅

### POST body の大きさ

| | 改修前 | 改修後 | 減 |
|---|---|---|---|
| 1匹 | 2,854,354 B (2.72 MB) | 992,990 B (0.95 MB) | **−65%**（−1.78 MB） |
| 2匹 | 2,196,692 B (2.09 MB) | 894,072 B (0.85 MB) | **−59%**（−1.24 MB） |
| 3匹 | 1,867,346 B (1.78 MB) | 851,482 B (0.81 MB) | **−54%**（−0.97 MB） |

匹数が増えるほど減り幅が小さいのは、同じ写真枠を匹数で割って描くため、合成
写真の PNG が匹数とともに小さくなるから。**いちばん多いのが1匹**で、そこが
いちばん軽くなる。

## 2. 送信にかかる時間

### 携帯回線（上り 750 kbit/s・遅延 150 ms）

| | build | send | 送信 合計 | 減 |
|---|---|---|---|---|
| 1匹 | 1,221 → 1,029 ms | 30,616 → 10,761 ms | **31,837 → 11,790 ms** | **−63%（−20.0秒）** |
| 2匹 | 1,089 → 1,012 ms | 23,594 → 9,706 ms | **24,675 → 10,718 ms** | **−57%（−14.0秒）** |
| 3匹 | 1,039 → 996 ms | 20,074 → 9,241 ms | **21,113 → 10,238 ms** | **−52%（−10.9秒）** |

実測の全数（送信 合計 ms、3回）:

```
  1匹  改修前 [31710, 31837, 32123]   改修後 [11790, 11790, 12312]
  2匹  改修前 [24651, 24675, 24698]   改修後 [10688, 10718, 10748]
  3匹  改修前 [21083, 21113, 21166]   改修後 [10201, 10238, 10268]
```

改修前の**いちばん速い回**より、改修後の**いちばん遅い回**のほうが速い。3回とも
重なりがない。

### localhost（回線の制限なし）

| | build | send | 送信 合計 |
|---|---|---|---|
| 1匹 | 1,034 → 1,062 ms | 29 → 7 ms | 1,066 → 1,076 ms |
| 2匹 | 959 → 1,006 ms | 26 → 7 ms | 988 → 1,013 ms |
| 3匹 | 968 → 930 ms | 11 → 6 ms | 979 → 938 ms |

```
  1匹  改修前 [1051, 1066, 1116]   改修後 [1033, 1076, 1107]
  2匹  改修前 [978, 988, 1067]     改修後 [882, 1013, 1019]
  3匹  改修前 [958, 979, 983]      改修後 [913, 938, 939]
```

**localhost では差が出ない**。合計のほとんどが入稿 PDF を描く時間（約1秒）で、
そこは変わらないため。送信そのもの（send）は 3〜4倍速くなっているが、元が
10〜30 ms なので合計では**ばらつきに埋もれる**。この条件で「速くなった」とは
書けない。

短くなるのは**回線を通る分**であって、計算する分ではない。

### 文字列にする時間（内訳）

build の中で唯一この改修が触る部分。実際に飛んだ payload を同じブラウザで
15回ずつ `JSON.stringify` した中央値（独立した2回の測定の幅）:

| | 写真あり | 写真なし |
|---|---|---|
| 1匹 | 5.6〜5.9 ms | 2.3〜2.4 ms |
| 2匹 | 3.7〜4.4 ms | 2.0〜2.1 ms |
| 3匹 | 3.2〜3.8 ms | 1.9〜2.1 ms |

**数 ms** の話で、build 全体（約1秒）から見れば誤差。時間が減るのは回線側。

**受入基準3（送信にかかる時間が短くなる）** ✅（携帯回線で 10.9〜20.0 秒短縮。
localhost では差は測れない）

## 3. 入稿データ（`print_base64`）は1画素も変わっていない

PDF の**バイト列は毎回違う**。ただしそれはこの改修のせいではなく、
`generateMeishiPrintPdf` がテンプレート・リボン・ロゴ・フォントを `Promise.all`
で同時に読み込んでいて、どれが先に終わるかが毎回違うことから来る
（`/CreationDate`、フォントのサブセットタグ、オブジェクトの並び順）。

対照として、**同じビルドを2回**走らせたものも同じように食い違うことを確認した。

| | 1匹 | 2匹 | 3匹 |
|---|---|---|---|
| 同じビルドを2回の `print_base64` バイト列 | 不一致 | 不一致 | 不一致 |
| 改修前 vs 改修後の `print_base64` バイト列 | 不一致 | 不一致 | 不一致 |

そこで PyMuPDF で描画して画素で比べた。

| 画素の差 | 350 dpi (841×1337) | 600 dpi (1441×2292) | 1200 dpi (2882×4583) |
|---|---|---|---|
| 改修前 vs 改修後 1匹 | **0 px** | **0 px** | **0 px** |
| 改修前 vs 改修後 2匹 | **0 px** | **0 px** | **0 px** |
| 改修前 vs 改修後 3匹 | **0 px** | **0 px** | **0 px** |
| 対照: 同じビルド2回 1匹/2匹/3匹 | **0 px** | **0 px** | **0 px** |

PDF の中身も直接突き合わせた。埋め込み画像・ページの内容ストリームは
**すべて sha256 まで一致**する。

```
改修前 vs 改修後  1匹
  same   content stream (179,485 B)
  same   image[0] 1046x1738 png (65,002 B)    テンプレート
  same   image[1] 682x584   png (633,208 B)   ペット写真（350 dpi ちょうど）
  same   image[2] 500x500   png (6,906 B)     anicas マーク
改修前 vs 改修後  2匹   content 179,890 B / image[1] 558,274 B  すべて一致
改修前 vs 改修後  3匹   content 180,284 B / image[1] 525,602 B  すべて一致
```

比較器が本当に差を見つけられることも確かめてある（1匹の PDF と2匹の PDF を
比べると 1200 dpi で 4,394,532 px が違い、内容ストリームも DIFFERENT と出る）。

**受入基準2（入稿データの中身が1画素も変わらない）** ✅

## 4. 画面の見た目と操作は変わっていない

同じ操作を改修前と改修後で通し、各画面をフルページで撮って画素で比べた
（390 × 844 の viewport、`deviceScaleFactor` 2）。

| 画面 | 1匹 | 2匹 | 3匹 |
|---|---|---|---|
| Step1 ペットの数 | 0 px | 0 px | 0 px |
| Step2 ペット情報 | 0 px | 0 px | 0 px |
| Step3 アカウント | 0 px | 0 px | 0 px |
| Step4 写真・プレビュー | 0 px | 0 px | 0 px |
| Step5 確認 | 0 px | 0 px | 0 px |
| 送信完了画面（完成カードつき） | 0 px | 0 px | 0 px |

18画面すべてで**1画素も違わない**。比較器の感度も確かめてある（1画素だけ色を
変えた画像を入れると「1 px / max diff 241」と出る）。

**受入基準4（画面の見た目と操作が変わっていない）** ✅
**受入基準5（1匹・2匹・3匹すべてで成立）** ✅ 上記すべての表が3匹分ある

## 5. 副作用として1つだけ変わること

作り直し・増刷のとき、写真の元は**入稿 PDF の中の 682 × 584px（350 dpi）**に
なる。単体で送っていたころは合成キャンバスそのもの（1200 × 1027px、印刷サイズ
換算で約 616 dpi）が別に届いていた。

印刷に使うのはどちらの場合も PDF の中の 350 dpi のほうなので、**刷り上がりは
変わらない**。変わるのは「PDF より高い解像度の原本が Drive に残らなくなる」点で、
GAS 側はすでにその原本を保存していない。

この環境で測れないのは1つだけ。

- LINE の中で実際に注文を1件通し、GAS 側で `{ig_handle}_print.pdf` が今まで

  立てているため、GAS 本体の挙動はここでは測れない）
