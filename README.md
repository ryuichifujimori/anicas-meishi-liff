# anicas 名刺フォーム LIFF

ペットタレントが名刺注文時に写真・情報を提出する LIFF フォーム。

## 技術スタック

- Next.js (App Router, TypeScript)
- Tailwind CSS v4
- LIFF SDK (`@line/liff`)
- `heic2any` (HEIC → JPEG 変換)
- データ送信先: Google Apps Script WebApp

## セットアップ

```bash
npm install
cp .env.local.example .env.local
# .env.local を編集して以下を設定
#   NEXT_PUBLIC_LIFF_ID=...
#   NEXT_PUBLIC_GAS_URL=...
npm run dev
```

## フォームのステップ

1. ペット数選択 (1〜3 匹)
2. 各ペットの種類・名前
3. Instagram ハンドル・IG NAME・オーナー名
4. 写真アップロード (HEIC 自動変換) ／ 写真の調整は名刺プレビューの中で／
   名刺プレビュー（プレビューの上で直接レイアウト）／「最初に戻す」
5. 確認 → GAS に POST → `liff.closeWindow()`

## QR コード生成

名刺の QR は実物名刺（c-cloud / qr.c-cloud.co.jp）と同じ `qr-code-styling`
ベースで **LIFF フロント側（ブラウザ）** で生成する。

- エンコード対象: `https://www.instagram.com/{ig_handle}`
- スタイル: `dotsOptions.type = "extra-rounded"` / `cornersSquareOptions.type = "dot"`
  （円形ファインダ枠）/ `cornersDotOptions.type = "dot"`（円形ファインダ中心）/
  黒一色・背景透明・`errorCorrectionLevel = "H"`
- 右下に `public/anicas_logo_br_square.png` を canvas 合成（中央固定の
  `image` オプションは使わない）。白い丸はファインダパターン（QRの目）と同じ
  7モジュール径で、「4つめの目」の位置に置く。3つのファインダパターン・
  タイミングパターン・形式情報には掛からない。
- **白い丸は動かさない・大きさも変えない。** `public/meishi-template.png` には
  元から anicas のマークが描かれていて、この丸がそれを覆っている。動かすと
  デザイン側のマークが下から出てきて**マークが2つ見える**（PR #9 で実際に起きた）。
- 丸の中のマークの大きさは `lib/meishi-layout.ts` の `LOGO_IN_DISC`。
  ロゴ画像の字面は円ではなく縦長なので、丸の **84.655%**（= 1 ÷ 1.18127）が
  はみ出さない最大。
- 生成ロジックは `lib/qr.ts`。プレビュー（`MeishiPreview`）と印刷用 PDF は
  **同一の data URL** を使うため完全一致する。
- `qr-code-styling` は DOM/canvas 依存のため GAS V8 では動かせない。QR 生成は
  フロントに一元化し、GAS 側の QuickChart 呼び出しは廃止する。

## 印刷用データ（PDF）の自動生成

送信時に、プレビューと同じ内容の **印刷所入稿用 PDF** をフロント側で生成して
ペイロードに載せる。イラレでの版下作成と飼い主確認のやり取りが不要になる。

- 用紙: **61 × 97 mm**（仕上がり 55 × 91 mm の一般的な名刺サイズ ＋ 塗り足し上下左右3mm）
- 色: RGB（CMYK 変換は試し刷り後に判断）
- 断裁位置は PDF の **TrimBox** に書き込み済み
- 中身の作り分け:

  | | PDF の中でのかたち |
  |---|---|
  | タレントが入力した文字（種類・名前・飼い主名・アカウント名） | 埋め込みフォントの**実テキスト**（選択・検索できる） |
  | QR | モジュールを**パス**として描画 |
  | テンプレート・リボン | 元の PNG をそのまま埋める（1046×1738 = **483dpi 相当**） |
  | anicas マーク | 500×500 の原本をそのまま埋める |
  | ペット写真 | 写真枠の大きさから逆算した画素数にリサンプル（**350dpi ちょうど**） |

  絵柄を輪郭にトレースするのは**やめている**。トレースは元画像の画素の階段を
  そのまま輪郭にしてしまい、肉球・Instagram の印・リボンの文字がかえって
  ガタつくため。元の PNG のままでも 483dpi あり、必要な 350dpi を上回る。

- ペットの文字は **1匹につき1列**（`layoutPets`）。列には種類が上・名前が下、
  同じ軸の上に乗る。**匹数で分岐していない**ので、4匹以上に増やすときも
  この規則のまま（今回は3匹まで）。
- 軸は「名前を1行に組んで字面で中央に置いた」結果そのものなので、1匹・2匹の
  名前の位置は従来と変わらない。種類だけが自分の名前の軸に乗る。
- 名前も種類も**折り返さない**。名前は文字を置ける範囲に収まる大きさまで、
  種類は隣の種類に 1em 以内まで近づかず範囲の端にも届かない大きさまで、
  それぞれ小さくなる。行の高さは design のまま保つので、字が小さくなっても
  下の行は動かない。**下限は設けていない**——はみ出さないことを優先している。
- 中央寄せの行は、行頭・行末の字が持つサイドベアリングを差し引いてから中央に
  置く。和文の字は全角の枠のなかで左右の余白が字ごとに違うため、送り幅の中央を
  揃えると**見えている字の中央がずれる**（種類と名前で 0.45mm）。

生成は `lib/print.ts` の `generateMeishiPrintPdf()`。送信ボタンの中には書かず、
`lib/submit.ts` の `buildSubmitPayload()` 経由で呼ぶ独立した関数にしてある
（決済をフローに入れたあと、決済完了後に同じ呼び出しをすればよい）。

レイアウトの定義は `lib/meishi-layout.ts` の1箇所だけ。画面プレビュー
（`MeishiPreview`）と印刷用レンダラ（`lib/print.ts`）が同じ比率から描くので、
片方だけずれることがない。

## プレビューの上で直接レイアウトする

ステップ4の名刺プレビューは、タレントが指でさわって直す場所でもある。

- さわれるのは **写真／ペットの列（匹数ぶん）** の2種類だけ。オーナー行・
  Instagram の行・QR・リボン・絵柄は動かない——どれもデザインが決めた場所に
  据わっているもので、動かせることに見合う値打ちがなかった。
- **ペットの列は1匹につき1つ**。1つの列にはそのペットの種類と名前が入っていて、
  列をさわると2行が一緒に選ばれて一緒に動く。匹数で分岐はしておらず、
  `text.pets` の数だけ列ができるので、4匹以上になっても規則は同じ。
- **動かせる部分には、編集画面のあいだずっと薄い点線の枠が出ている。**
  触るとその枠が実線になる。枠の外を触ると外れる。覚える状態は「いまどれを選んで
  いるか」の1つだけ。確認画面（ステップ5）には点線を出さない——そこで完成形を見るため。
- **写真の窓は匹数ぶんの区画に左右へ均等に分かれ、区画ごとにさわれる。** 1匹なら区画は
  1つ＝写真ぜんたい。**指2本（ピンチ）でその区画の絵が大きく／小さく**、**指1本で動く**。
  角のつまみは無い——実寸3ミリの丸を狙って引く操作は、教わらなければ思いつかないため。
  読み取るのは2本の指の**中点・間隔・傾き**で（`Grip`）、大きさに使うのは間隔だけ。
  傾きも最初から読んでいるので、回転を足すときは `onMove` の1行で済む。ペットの列に
  ピンチは付いていない（大きさは「文字の大きさ」）。
- **写真の編集画面は無い。** 絵の合成（透明な地に区画ごとに cover-fit）は
  `lib/photo-slots.ts` にあり、名刺プレビューがその canvas を直接カードに描く。入稿PDFと
  payload に渡すデータURLは、指が止まってから作る。区画の値は `FaceAdjust.photos` に
  区画ごとの配列で持つので、写真の入れ替えは元の絵が替わるだけで済む。
- 横に動かしているあいだだけ、**中央や等間隔の位置でぴたっと止まり**、
  なぜ止まったかを示す印が出る。指を離すと消える。
- **指でつかんでいる間、指の動きはカードが受け取り、ページはスクロールしない。**
  スマホは最初の1回の動きで「この指はスクロールか」を決め、スクロールだと決めると
  ポインタを取り上げてしまう（`pointercancel`）ので、`touch-action: none` に頼らず
  `preventDefault` ではっきり断っている（React の touch リスナーは passive なので、
  素の `addEventListener(..., { passive: false })` で付ける）。断るのは**つかんでいる
  間だけ**なので、名刺の外は今までどおりスクロールする。つまみの当たり判定は 44px、
  ポインタの捕捉先はつまみではなくカード全体。
- できるのは **動かす（指1本）／大きさを変える（指2本）** の2つ。ただし**ペットの列は
  動かすだけ**で、大きさはプレビューの下の「文字の大きさ」で全部の列いっしょに決める。
- **写真は窓が動かない。** さわって動かす・大きくするのは窓の中の絵のほうで、
  描かれる範囲はどんな大きさにしてもデザインの窓のまま（下の項）。
- 位置と大きさは `lib/card-adjust.ts` が**面ごとのまとまり**として持つ
  （`{ front: { photo, pets: [...], text } }`）。プレビューと入稿PDFは
  この1つの結果から描くので、指の下で見えているものと印刷所に届くものが必ず一致する。
  裏面を足すときは `back` を隣に足すだけでよい。

**ペットの列は横にしか動かない。** `ColumnAdjust` は `dx` しか持たない。`dy` が
ないのは、種類は1本のベースライン、名前はもう1本のベースラインを匹数ぶんで
共有していて、1匹だけ上下にずれると揃わなくなるため。`scale` がないのは次項。

### 文字の大きさは枠の外で、全部の列にいっぺんに

列の角を引いて大きさを変える形だと、**3匹の名前を同じ大きさに揃えるのが難しい**。
名刺が見られるのはまさにそこなので、大きさはプレビューの下の「文字の大きさ」1つに
まとめ、`FaceAdjust.text` として面ごとに持つ。押し込むと全部の列が同じ倍率になり、
**その大きさで収まらない列だけが、その列の中で自動的に小さくなる**
（`clampColumn` が隣の列と 2.0mm の余白から許される倍率を出し、行ごとの下限は
`heldSize` が受け止める——規則は前からのものをそのまま使う）。

プレビューでは**行の外側の span が行の級数で line box を持ち**、その中の span
（高さを持たない）に各ペットの字を入れるので、どの大きさでも字は同じベースラインに
乗る。入稿PDFも同じで、ベースラインは行の級数から、字の大きさは列ごとの級数から。

崩れない仕組みは `clampAdjust` の1か所に集めてある。値は**しまう前に**通すので、
保存された値も、いま指で引いている値も、同じ規則で丸められる。

| | 止まるところ |
|---|---|
| 全部 | 名刺の仕上がり枠（55×91mm）の外に出ない |
| ペットの列 | 仕上がり枠の左右それぞれ内側 `SAFE_MARGIN`（2.0mm）に入らない。断裁がぶれても切れないため。写真だけは例外で端まで届く |
| ペットの列 | 隣の列に届く手前で止まる（動かすときも、文字を大きくするときも） |
| 写真 | **リボンの輪郭（`PHOTO_CLIP`）より下には描かれない。** わく自体は動かせるが、絵はその線より上だけ——動かす・大きくするは、その形の中での寄せと拡大になる |
| 文字 | `MIN_TYPE_SIZE` より小さくならない。**行の種類ごとに別の下限**を持つ：名前 3.0mm／種類 1.8mm |

列を縮めていくと、**先に種類が 1.8mm で止まり、名前だけが 3.0mm まで縮み続ける**。
列の下限は「最後に下限へ届く行」＝ふつうは名前が決める（`columnFloor`）。
すでに詰め込みで下限を割っている行は、下限まで**押し上げない**——縮められないだけ。

### 写真の窓は動かない。動くのは窓の中の絵

写真の**窓**——描かれる範囲——は**カードに据わっていて、動きも広がりもしない**。
さわって動かす・大きくするのは窓の**うしろの絵**のほうで、窓からはみ出した分は
描かれない。だから写真をどれだけ大きくしても、リボンの左右から顔を出すことも
カードの端まで広がることもない。

窓は3辺がデザインの写真枠そのもの（`LAYOUT.photo` ＝ 2.750〜52.250mm、上端
2.457mm）で、**下辺だけがリボンの輪郭**。

### 下辺はリボンの輪郭で切る（四角では合わない）

リボンの左右の端は**斜め**なので、写真を四角で合わせようとすると必ずどちらかが
起きる——広げれば、ある高さでひらひらの外に角が出る。狭めれば、別の高さで写真と
ひらひらの間に白いすき間ができる。実際に両方やって、両方見えた。

そこで下辺は**リボンの輪郭そのもの**で切っている。

`scripts/build-ribbon-profile.sh` が `public/meishi-ribbon.png` を読み、横方向の
位置ごとに「リボンが上から見て最初に不透明になる行」と「そこから続く不透明な区間の
長さ」を求める。線はその2つが作る帯の中に入っていなければならない:

| | 越えると |
|---|---|
| 最初に不透明になる行より**上** | 写真とリボンの間に白い紙が見える |
| 最初の不透明な区間より**下** | 写真がリボンの外に顔を出す |

線は帯の中でまっすぐ伸ばせるところまで伸ばして単純化してある。単純化した線が本当に
全列で帯の中にあるかは、**書き出す前に列あたり16点で確かめている**（外れたらスクリプトが
止まる）。ひらひらの肩のようにリボンの縁がほぼ真上に立つところでは、線も同じ x のまま
真上に立つ（同じ x を持つ点が2つ並ぶ）。結果は **14点**で、線はリボンの縁の
**2.0〜6.5 行下**——写真は必ず少しだけリボンの下にもぐり込んで終わる。

書き出し先は `lib/ribbon-profile.ts`。**実行時に PNG を読み直すことはない。**
リボンの絵を差し替えたら、このスクリプトを実行し直すだけでよい。

切り抜きの**左右はリボンが届く範囲そのもの**（`RIBBON_SPAN`）。先より外側には、どの高さ
にもリボンが無い——先はどの行でもリボンのいちばん端で、先より下ではひらひらは内側へ戻る
——ので、そこに写真があると下端をどう切っても開けたところに残る。実物の名刺の写真も
リボンの範囲そのまま（2.892〜52.108 mm）で、窓の .05／.95 は丸めた設計値のほうが左右に
0.15〜0.19 mm 広い。枠の値は変えず、切り抜きだけをリボンの端で止めている。

`lib/meishi-layout.ts` の **`photoClip()` が唯一の定義**で、プレビューは
`clip-path: polygon()`、入稿PDFはクリップパスにする。形が2つに分かれることはない
（実測で最大のずれ 0.0024mm）。

`photoClip()` は絵の箱を受け取る。**絵が届いていない辺は、切らずにカードの外へ
逃がす**——切る線を絵のふちにぴったり重ねると、描画側がそのふちを二度描いて
1画素ぶん色が変わってしまうため。逃がすのは「切るものが無い辺」だけなので、
窓の外に絵が出ることはない。

窓の**下端**は実物の名刺 `public/sample-meishi.png` から測った位置のまま。実物を
テンプレートに重ねて（リボンの輪郭が両方にあるので、それで合わせる）読むと、実物の
写真の下端はカード箱の **.49244**。`LAYOUT.photo` は `top .029 + height .4634 = .4924`
でそこに合わせてある。**左右はデザイン本来の .05／.95（2.750〜52.250mm）**。

### 中央や等間隔でぴたっと止まる

止まる位置は `lib/card-adjust.ts` の **`SNAP_TABLE` という1つの表**にしてある。
横に動かしているあいだ、表のどれかに 1.5mm より近づくとそこで止まり、印が出る。
印は指を離すと消える（常設しない）。

| 表の行 | 止まる位置 | 出る印 |
|---|---|---|
| カードの中央 | 名刺の中央（27.5mm） | カードを縦に貫く細い線1本 |
| 隣とのすき間が等しくなるところ | 左右にあるもの（隣の列、なければ余白）のちょうど真ん中 | すき間ごとに**同じ長さの横線**——2本並んで「等しい」と言う |

印は表の行が自分で決める（`SnapRule.mark`）ので、増やすときは表に1行足すだけ。
ドラッグ、出る印、しまわれる値のすべてがこの表から出ている。写真だけは対象外——
窓がカードに据わっていて、揃える相手がないため。

「最初に戻す」は1つだけ置いてある。押すと写真も列も既定の位置と大きさに戻る。

実測値・比較画像・QR デコード結果:

- `docs/direct-edit-verification.md` … 最新（プレビュー上の直接編集・ペットごとの列・はみ出し・最小サイズ）
- `docs/print-quality-verification.md` … 絵柄の輪郭・中心・間隔バー・ロゴ径
- `docs/print-vector-verification.md` … 文字の実テキスト化と QR のパス化
- `docs/print-pdf-verification.md` … PDF 生成そのものを入れたとき

## GAS への送信ペイロード

```json
{
  "ig_handle": "kotetsutokotatsu",
  "ig_name": "YUKO",
  "owner_name": "金野祐子",
  "pets": [{ "breed": "ポメラニアン", "name": "コテツ" }],
  "photo_base64": "data:image/png;base64,...",
  "print_base64": "data:application/pdf;base64,...",
  "adjust": {
    "front": {
      "photo": { "dx": 0, "dy": 0, "scale": 1 },
      "pets":  [{ "dx": 0 }],
      "text":  1
    }
  },
  "line_user_id": "Uxxxx"
}
```

- `photo_base64` … 合成済みのペット写真。作り直し・増刷のときに原本が要るので残す。
- `print_base64` … 印刷用 PDF（data URL）。`{ig_handle}_print.pdf` として保存する。
- `adjust` … タレントがプレビューの上で動かした位置と大きさ。面ごと（いまは
  `front` のみ）に、写真は `dx`／`dy`（カード幅・高さに対する割合）と `scale`
  （既定の何倍か）、ペットの列は `pets` の配列で `dx` だけ（列は縦に動かず、
  大きさも持たない）、文字の大きさは面ごとの `text` 1つ。何も触っていなければ
  `pets` は空配列、`text` は 1、写真は `dx:0, dy:0, scale:1`。作り直しのときに
  同じレイアウトで組み直せるように残す。GAS 側で使わないなら無視してよい。
  **`name_spread` は廃止**（「名前の間隔」のバーごとなくなった）。
  **`ig` と `qr` も廃止**（Instagram の行と QR は動かせなくなった）。
- `qr_base64` は **廃止**。QR は `print_base64` の中に描かれているため、
  単体で送る必要がなくなった。

> **GAS WebApp 側の変更が必要**（本リポジトリには GAS ソースは含まれない）:
> 1. `doPost` で `print_base64` を取り出し、既存の base64→Drive 保存処理を流用して
>    `{ig_handle}_print.pdf` を保存する（MIME は `application/pdf`）。
> 2. `qr_base64` を受け取って `{ig_handle}_qr.png` を保存していた処理を削除する。
>    （旧来の QuickChart による QR 生成もすでに不要）
> 3. 既存の Drive フォルダ ID・スプレッドシート追記ロジックはそのまま流用。
> 4. **デプロイ→デプロイを管理→新バージョン** で再デプロイする（コード push だけでは
>    本番反映されない）。WebApp URL は変更しない。
